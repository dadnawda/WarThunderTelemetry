# WarThunderTelemetry 项目规划书 v1.0

> 基于 War Thunder 本地 8111 接口的飞行数据辅助软件
> 技术栈：WinUI 3 + .NET 10 + Windows App SDK
> 开发环境：Visual Studio 2026
> 规划日期：2026-09-29

---

## 一、项目定位与合规边界

### 1.1 这是什么

一个**只读**的本地遥测数据显示工具。War Thunder 游戏本体在 `http://127.0.0.1:8111` 暴露了一套官方的本地 HTTP 接口，本软件通过标准 HTTP 轮询读取这些 JSON 数据，然后以悬浮窗的形式叠加显示在游戏画面上。

### 1.2 合规边界（必须遵守的红线）

| 项目 | 说明 |
| --- | --- |
| **不注入游戏进程** | 不使用 DLL 注入、不 Hook DirectX/Vulkan、不读写游戏内存 |
| **不修改游戏文件** | 不触碰游戏安装目录的任何文件 |
| **不模拟输入** | 不发送键鼠事件、不操控游戏 |
| **不绕反作弊** | 不接触 EasyAntiCheat，不尝试绕过任何检测 |
| **纯数据消费方** | 只做 HTTP GET 请求，与浏览器打开 `localhost:8111` 无本质区别 |

**风险提示**：8111 接口是**官方公开的本地接口**（游戏 `选项 → 游戏 → War Thunder 接口` 中可开关），读取它是被设计允许的行为。但部分对战模式（历史/全真）中，利用接口信息获得不对称优势可能违反游戏行为准则。**本工具的定位是「个人数据仪表 / 直播展示 / 录像分析」，不建议在对战中使用。**

### 1.3 与参考项目的关系

参考项目 [`lcyksp/War-Thunder-8111-Port`](https://github.com/lcyksp/War-Thunder-8111-Port) 是 Electron 实现（JS + Chromium，约 280MB 运行时）。本项目是**原生重写**：

| 对比项 | 参考项目 (Electron) | 本项目 (WinUI 3) |
| --- | --- | --- |
| 内存占用 | 300~500 MB | 60~120 MB |
| 启动速度 | 2~4 秒 | < 1 秒 |
| 安装体积 | ~280 MB | ~40 MB（自包含 ~90MB） |
| 悬浮窗透明 | 支持 | 支持（需配置） |
| 后续扩展 | 受限于 JS 生态 | 原生，可接 C++/GPU 绘制 |

参考项目已解决的**关键工程问题**（本项目直接复用其结论）：
1. 8111 接口字段名极不稳定，必须做**多别名容错解析**（`/state` 用 `H, m`、`Vy, m/s`、`Ny`、`Mfuel, kg`；`/indicators` 用 `compass`、`g_meter`、`gears`、`vario`、`type`）。
2. 各端点必须**独立轮询、独立容错**，任一失败不影响其他数据。
3. `/hudmsg` 与 `/gamechat` 用**游标增量拉取**，避免重复推送。
4. 悬浮窗锁定后需 `点击穿透`，否则会挡住游戏操作。
5. HUD 窗口必须**禁用后台节流**，否则游戏获得焦点时刷新停摆。

## 二、技术选型

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| UI 框架 | **WinUI 3**（Windows App SDK 1.7+） | 你的硬性要求；原生流畅、支持无边框透明窗 |
| 运行时 | **.NET 10**（或 .NET 9，按 VS2026 默认） | WinUI 3 官方支持，性能好 |
| 语言 | **C# 13** | — |
| HTTP | `System.Net.Http.HttpClient` + `System.Text.Json` | 内置，AOT 友好，零第三方依赖 |
| 悬浮窗 | WinUI 3 `Window` + `OverlappedPresenter` + Win32 互操作 | 透明/置顶/穿透需要少量 P/Invoke |
| 配置持久化 | JSON 文件（`%LocalAppData%`） | 简单可靠，便于用户手改 |
| 单元测试 | xUnit | 解析器逻辑必须可测 |
| MVVM | `CommunityToolkit.Mvvm`（可选） | 若走 MVVM 推荐，减少样板代码 |

### 2.1 唯一需要额外的依赖

WinUI 3 的**窗口透明 + 点击穿透**能力比 WPF 弱，需要少量 Win32 互操作。这部分我会直接写在代码里（P/Invoke 调用 `SetWindowLongPtr` / `SetLayeredWindowAttributes`），**不需要额外 NuGet 包**。

## 三、架构设计

### 3.1 分层结构（关键：采集与显示解耦）

```
┌─────────────────────────────────────────────────────────┐
│  WarThunderTelemetry.App  (WinUI 3 可执行程序)           │
│  ├── 主窗口：仪表盘 / 全字段表格 / 地图 / 信息流          │
│  └── 悬浮窗 HUD：透明置顶、可锁定穿透                     │
└──────────────────────┬──────────────────────────────────┘
                       │ 依赖（事件订阅）
┌──────────────────────▼──────────────────────────────────┐
│  WarThunderTelemetry.Core  (类库，零 UI 依赖)            │
│  ├── TelemetryClient      8111 轮询引擎（多端点并发）     │
│  ├── TelemetryState       线程安全的数据快照              │
│  ├── Parsers/             别名容错字段解析器              │
│  ├── DerivedMetrics       性能派生指标引擎                │
│  ├── Alerts/              告警规则引擎（可扩展）           │
│  └── Models/              强类型数据模型                  │
└──────────────────────┬──────────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────────┐
│  WarThunderTelemetry.MockServer (工具/测试辅助)          │
│  本地模拟 8111 服务，无游戏也能开发调试                    │
└─────────────────────────────────────────────────────────┘
```

**为什么这样分**：Core 完全不依赖 UI。以后你要加 Web 端、移动端、OBS 插件、AI 分析、录制器，全部直接引用 Core，一行显示代码都不用重写。这是你选的「独立后台服务 + 前端解耦」。

### 3.2 扩展点设计（为后续功能预留）

| 扩展点 | 接口 | 后续可接的功能 |
| --- | --- | --- |
| **数据源** | `ITelemetrySource` | 8111 HTTP / 本地日志回放 / 录像文件 |
| **指标计算** | `IMetricProvider` | 能量机动评分、最佳缠斗速度、推力估算 |
| **告警规则** | `IAlertRule` | 失速预警、超速预警、过载预警、燃油告警 |
| **显示面板** | `IDashboardPanel` | 插件式添加新面板（雷达图、曲线图、数据分析） |
| **数据导出** | `ITelemetrySink` | CSV 记录、飞行日志、AI 复盘 |

第一阶段只实现接口 + 少量内置实现，后续你加新功能只需新增一个实现类并注册。

### 3.3 数据流

```
8111 HTTP ──► TelemetryClient（各端点独立定时器）
                    │
                    ├─► 解析器（多别名匹配）
                    │
                    ├─► TelemetryState（不可变快照，事件通知）
                    │        │
                    │        ├─► DerivedMetrics 计算派生值
                    │        │
                    │        ├─► AlertEngine 评估告警
                    │        │
                    │        └─► Sink 落盘（可选）
                    │
                    └─► UI 层订阅 StateChanged 事件（DispatcherQueue 切主线程）
```

**性能要点**：
- UI 更新用 **30~60Hz 合并帧**（`CompositionTarget.Rendering` 或定时节流），不做逐条数据渲染，避免数据风暴拖垮 UI。
- 悬浮窗**禁用后台节流**：`AppWindow` 无法直接禁用，需 P/Invoke `DwmSetWindowAttribute` + 保持窗口始终置顶；实测 WinUI 3 窗口在游戏全屏焦点下仍会刷新（非 UWP），若出现停摆再补 `SetThreadExecutionState`。
- 环形缓冲：事件流、聊天、轨迹点均设上限（如 200 条），内存恒定。

### 3.4 载具参数与告警阈值的获取策略（v1.1 修订）

> **本章为 v1.1 新增。** 初版规划采用「一次性录入 40~60 架的静态内置库、全程不联网」，
> 现已改为 **运行时按需联网解析 + 本地缓存**，静态库降级为二级来源。

**为什么要改**：机型数量远超预期（wiki 全量 1324 条），手工录入既覆盖不全又极易出错；
而告警阈值的准确性直接决定告警可信度 —— 阈值错了，辅助工具就变成干扰工具。

**四级阈值来源（按优先级）**：

| 级别 | 来源 | 说明 |
| --- | --- | --- |
| 1 | **本地缓存** | `%LocalAppData%\WarThunderTelemetry\vehicle-cache.json`，命中即用，零延迟 |
| 2 | **内置参数库** | 嵌入资源 `VehicleData.json`，覆盖常见机型，断网可用 |
| 3 | **联网 wiki** | `wiki.warthunder.com` unit 页面实时解析，成功后写入缓存 |
| 4 | **兵种兜底** | 战斗机 / 攻击机 / 轰炸机 / 直升机各一套保守缺省阈值 |

**抓取时机**：**首次遇到新载具时才抓**（不是开机全量预抓）。
用户进入某架飞机 → `Resolve()` 发现未收录 → 立即用兜底阈值保证功能不中断 →
同时在后台异步抓取并缓存 → 下次同机型直接走缓存。

**并发控制**：`ConcurrentDictionary<string, Task<VehicleProfile?>>` 做请求去重，
同一载具被并发请求时只真正抓一次。

**实现组件**：

| 组件 | 职责 |
| --- | --- |
| `WikiPageParser` | 用 `[GeneratedRegex]` 解析 unit 页：`gameId`、名称、G 限、襟翼限速、爬升率、回转时间、实用升限 |
| `VehicleSlugIndex` | 加载嵌入的 1324 条 slug 索引，供匹配用 |
| `OnlineVehicleResolver` | 编排四级来源、并发去重、缓存读写、原子落盘 |

**关键设计决策：刻意不做激进模糊匹配。**
游戏侧与 wiki 侧的载具代号存在**真实且不规则的差异**，例如：
- 游戏侧 `spitfire_mk9` ↔ wiki 侧 `spitfire_ix`（阿拉伯数字 vs 罗马数字）
- wiki 侧还有 `bf-109f-4`、`a6m2_zero` 这类不规则命名

若做激进模糊匹配，会把 A 机的阈值安到 B 机上 ——
**这比「抓不到而回退兵种兜底」更危险**，因为用户无法察觉阈值是错的。
因此匹配只做三级保守策略：完全相同 → 分隔符互换 → 去分隔符归一；
仍不匹配则明确回退兜底，不做猜测。

**已实测的网络可达性**：
- `wiki.warthunder.com` ✅ 可达
- `wtvehiclesapi.duckdns.org` ❌ DNS 通但 443 不通
- `raw.githubusercontent.com` ❌ 不可达

原计划的「wiki 优先、第三方 API 回退」中，回退源实测不可达，
故回退链路**保留接口但留空**，不报错、不影响主流程。

**联网开关**：设置页可关闭 `OnlineVehicleLookup`，关闭后只走缓存 + 内置库 + 兵种兜底。

### 3.5 部署形态：必须自包含（SelfContained）

> **踩坑记录，不可回退为框架依赖模式。**

非打包（`WindowsPackageType=None`）应用在启动时，
`WindowsAppRuntime.Bootstrap` 要求目标机同时具备三个包：
**Framework + Main + Singleton**。

本机 Framework 包齐备（`Microsoft.WindowsAppRuntime.1.6_6000.519.329.0`，x64/x86，Status=Ok），
但 **Main 与 Singleton 包缺失** → 引导程序在托管入口点之前就终止进程。

**症状特征**（便于日后快速识别）：
- 弹框提示「This application requires the Windows App Runtime Version 1.6」
- 进程退出码 `0x80670016`（有符号 `-2140733418`）
- **不产生任何托管输出**：stdout 为空、`crash.log` 不生成
- 注意弹框中的版本号提示具有误导性 —— 本机版本 519 实际高于要求的 424

**采用的对策**：

```xml
<SelfContained>true</SelfContained>
<WindowsAppSDKSelfContained>true</WindowsAppSDKSelfContained>
```

自包含后运行时 DLL 随程序输出（`Microsoft.WindowsAppRuntime.dll`、`MRM.dll`、
`CoreMessagingXP.dll` 等，bin 目录 DLL 从 21 个增至 242 个），
**完全绕过系统引导程序**，不再依赖目标机预装。

**代价与收益**：输出体积增大；换来的是换机器、交付他人时的确定性。
对一个要拿到别人机器上跑的工具而言，这个交换是值得的。

## 四、8111 接口字段清单（第一期用到的）

### 4.1 端点总览

| 端点 | 用途 | 轮询间隔（建议） | 第一期 |
| --- | --- | --- | --- |
| `GET /state` | 飞机原始状态（速度/高度/舵面/油量/温度） | 100~200 ms | ✅ |
| `GET /indicators` | 仪表盘数据（航向/过载/起落架/俯仰滚转） | 200~250 ms | ✅ |
| `GET /map_info.json` | 地图元数据（地图名/模式/玩家列表/自己的武器） | 1000 ms | ✅ 连接探针 |
| `GET /mission.json` | 任务目标与进度 | 2000 ms | ⏳ 二期 |
| `GET /map_obj.json` | 全部单位位置/速度/朝向 | 200 ms | ⏳ 二期（战术地图） |
| `GET /hudmsg?lastEvt=&lastDmg=` | 击杀/伤害事件流 | 500 ms | ⏳ 二期 |
| `GET /gamechat?lastId=` | 战斗聊天 | 1000 ms | ⏳ 二期 |
| `GET /map.img` | 地图底图 PNG | 按需 | ⏳ 二期 |

### 4.2 `/state` 关键字段（真实字段名）

| 字段名（真实） | 含义 | 单位 |
| --- | --- | --- |
| `H, m` | 海拔高度 | 米 |
| `IAS, km/h` | 指示空速 | km/h |
| `TAS, km/h` | 真空速 | km/h |
| `M` | 马赫数 | — |
| `Vy, m/s` | 垂直速度（爬升率） | m/s |
| `Ny` | 纵向过载 | g |
| `AoA, deg` | 迎角 | 度 |
| `AoS, deg` | 侧滑角 | 度 |
| `Wx, deg/s` | 滚转率 | 度/秒 |
| `Mfuel, kg` / `Mfuel0, kg` | 当前/初始燃油 | kg |
| `throttle N, %` | 第 N 台发动机油门 | % |
| `RPM N` | 第 N 台发动机转速 | rpm |
| `oil temp N, C` / `water temp N, C` | 油温/水温 | ℃ |
| `aileron, %` / `elevator, %` / `rudder, %` | 舵面偏度 | % |
| `flaps, %` | 襟翼 | % |
| `gears, %`（部分机型） | 起落架 | % |

### 4.3 `/indicators` 关键字段（真实字段名）

| 字段名（真实） | 含义 | 单位 |
| --- | --- | --- |
| `compass` | 航向（**注意不是 heading**） | 度 |
| `g_meter` | 过载表（**注意不是 Ny**，与 state 的 N 值互为补充） | g |
| `vario` | 垂直速度表 | m/s |
| `gears` | 起落架状态（0~1 或 DOWN/UP） | — |
| `flaps` | 襟翼状态 | — |
| `type` | 机型内部代号 | — |
| `aviahorizon_pitch` | 地平仪俯仰 | 度 |
| `aviahorizon_roll` | 地平仪滚转（坡度） | 度 |
| `speed` | 表速（字符串） | km/h |
| `throttle` | 油门（0~1） | — |
| `mach` | 马赫 | — |

> ⚠️ **重要**：不同机型/模式下字段缺失是常态（如活塞机没有 `oil temp`、部分载具没有 `M`）。解析器必须**全部走别名容错 + 空值降级**，缺字段显示 `–` 而不是报错或空白行。

### 4.4 性能派生指标（游戏不提供，本地计算）

| 指标 | 公式 | 实现要点 |
| --- | --- | --- |
| 加速度 | `a = ΔV / Δt` | 取 ≥1.2s 长窗口差分，EMA 平滑 |
| 能量高度 | `E = h + V² / 2g` | 需真实 TAS，IAS 估算误差大 |
| 爬升角 | `γ = asin(Vy / V)` | 角度制 |
| 回转率 | `ω = Δcompass / Δt` | 航向差归一化到 ±180° 再求导，EMA 平滑 |
| 回转半径 | `r = V / ω(rad)` | `|ω| > 3°/s` 才有效，上限 50km 过滤奇异值 |
| 盘旋 360° 耗时 | `t = 360 / |ω|` | — |
| 俯仰/坡度 | 直接取 `aviahorizon_pitch` / `aviahorizon_roll` | — |

## 五、功能分期

### 第一期：MVP（本次交付）

**目标**：能连上游戏、能看到数据、能浮在游戏上。

| # | 功能 | 说明 |
| --- | --- | --- |
| 1 | 8111 连接引擎 | 自动探测、断线重连、多端点并发轮询 |
| 2 | 别名容错解析器 | 全字段防御性解析，缺字段不崩 |
| 3 | **主窗口仪表盘** | 核心飞行数据卡片（速度/高度/爬升/油门/过载/油量/航向） |
| 4 | **全字段实时表格** | `/state` + `/indicators` 每个字段都列出，支持搜索筛选 |
| 5 | **悬浮窗 HUD** | 透明底、置顶、可拖动、字号/颜色/字段可配、**锁定后点击穿透** |
| 6 | **告警/状态指示** | 失速、超速、过载、低油量、起落架、襟翼状态着色 |
| 7 | 派生指标引擎 | 加速度、能量高度、回转率、回转半径、盘旋耗时 |
| 8 | 模拟数据服务器 | 无游戏时可完整调试全部界面 |
| 9 | 配置持久化 | 窗口位置、HUD 配置、显示字段全部记住 |

**验收标准**：
- 启动战雷进入战斗 → 3 秒内自动连上，数据实时刷新
- 关掉战雷 → 状态指示变灰，不崩溃，恢复后自动重连
- 悬浮窗锁定 → 鼠标点击穿透到游戏，不影响任何操作
- 断网/无游戏启动 → 显示「未连接」，可用模拟模式调试

### 第二期：战术地图 + 信息流

- 战术地图面板：实时绘制自己/友军/敌军位置、轨迹、朝向箭头
- 战斗信息流：击杀/伤害事件（按类型着色）、战斗聊天、任务目标进度
- 地图底图加载（`/map.img`）

### 第三期：分析与扩展

- 飞行数据记录（CSV / 自研格式）
- 飞行曲线图（速度-时间、高度-时间、能量-时间）
- 能量机动评估、最佳缠斗速度提示
- 可配置告警规则（用户自定义阈值）
- 插件式面板系统

## 六、关键技术风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **WinUI 3 窗口透明+穿透实现复杂** | 悬浮窗可能显示黑底或无法穿透 | 已准备方案：`OverlappedPresenter` + `SetWindowLongPtr(GWL_EXSTYLE, WS_EX_LAYERED\|WS_EX_TRANSPARENT)` + `SetLayeredWindowAttributes`。**这是最大技术风险点，会在第一阶段最先验证** |
| WinUI 3 窗口在游戏独占全屏下被覆盖 | 悬浮窗看不见 | 游戏需设为**无边框窗口**或**窗口化**；独占全屏下所有非注入叠加层都无法显示，这是 Windows 合成器的限制，非本项目缺陷 |
| 游戏更新导致字段改名 | 数据显示空白 | 别名容错解析器 + 全字段动态表格（游戏给什么显示什么） |
| 轮询过频导致 CPU 占用 | 游戏卡顿 | 各端点独立间隔 + 自适应降频（游戏失焦时降低频率，可选） |
| 游戏未开启接口 | 连接失败 | 明确的引导提示：`选项 → 游戏 → War Thunder 接口` 需启用 |
| VS2026 模板/版本兼容 | 项目无法打开 | 我会生成标准 SDK 风格项目文件，手写而非依赖模板，兼容 VS2022/2026 |
